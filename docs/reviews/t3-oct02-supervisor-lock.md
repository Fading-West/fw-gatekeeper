# Enforce supervisor lock on the kiosk server

Locking previously cleared one browser cookie while copies remained authorized until expiry. Session issuance now has unique random identity and an in-process registry; lock revokes that session, including copies, while independent supervisor sessions remain usable. Restart requires a fresh unlock, so revoked tokens cannot revive. TTL, PIN/UI-key signing and existing attempt limits remain enforced. The UI hides controls immediately and offers a retry if server locking cannot be confirmed.

Scope: master-based supervisor-session lifecycle only. Compose with PR98 history authorization and rank1 manual-operation durability without altering their behavior.

Review correction: the UI claims a single unlock operation synchronously, ignores late success after cancellation/locking, and requires confirmed locking before retrying uncertain unlock. Lock names the operation as well as its cookie. The server retains cancellation tombstones for the process lifetime, so a delayed request cannot mint a credential after lock; a delayed Set-Cookie contains an already revoked token. Separate supervisor sessions remain independent. Every unlock caller must now supply the current public boot nonce from /health or the existing /status snapshot; it is a process generation identifier, not an authentication credential. A delayed pre-restart operation cannot mint a new session after cancellation tombstones are reset. The page waits for status and requires a fresh explicit unlock after a generation change. Synthetic regression source covers double submission, cancellation during pending unlock, lock before token creation, token creation before lock, and cancel/restart/late-request rejection followed by an explicit fresh unlock. No checks were executed during this correction; only git diff --check.

Source follow-up: operation generation now occurs inside try/finally and falls back from randomUUID to cryptographic getRandomValues. Missing or throwing secure randomness sends no request and releases the submit guard for recovery. Actual-handler fixtures cover missing/throwing generation, fallback single flight, and fallback cancellation. The existing worker-selection fixture now obtains its cookie through the normal protected unlock endpoint before preserving its ambiguous-name rejection and specific-worker-ID assertions. Hung-response recovery correction: confirmed server locking now retires the active client unlock generation, releases its submit guard and aborts its fetch. Failed or unconfirmed locking retains the operation and blocks a fresh unlock. Success, catch and finally callbacks check their originating generation, so an old response cannot reveal controls, replace the current operation owner or release a newer in-flight guard. Server operation tombstones and boot-generation checks remain unchanged; client abort alone does not revoke authority.

The actual-handler regression leaves an old unlock unresolved, verifies failed lock confirmation cannot retire it, confirms a retry of that same lock, and starts a fresh explicit unlock without waiting for the old response. Its fetch deliberately ignores abort and later delivers old success both while the new request is pending and after new success, exercising stale success/finally ownership.
