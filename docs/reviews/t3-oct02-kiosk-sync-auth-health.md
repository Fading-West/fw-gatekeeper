# Show protected sync authorization faults independently of reachability

Public /api/health can succeed while a protected route denies the kiosk key. SyncAuthHealth records roster download, roster acknowledgement, attendance upload, and recognition upload independently. A 401/403 marks that phase denied; only a later 2xx from that same protected phase clears it. Other successful phases, public reachability, network failure and 5xx responses cannot erase a denial. State is process-local and starts unknown after restart; it does not claim a key is valid before an observed protected response.

Local /health and the kiosk footer show authorization needs attention, the affected workflows, and existing queue/rejection counts even while the public server is reachable. The sync worker reports faults at every cycle boundary, including interrupted cycles. Scanner/manual local attendance remains operational. No PIN or API-key values are exposed. An idle phase with no queued requests retains its observed fault until that phase actually succeeds again.

Scope: master-based protected-response observations and local health/UI only. Preserve old PR95 roster commit acknowledgements, PR97 complete batch acknowledgements, PR99 vector validation, PR107 recognition quarantine/acks, and rank12 independent sync phases on composition. Move the recognition observation into PR107's _upload_recognition request helper so every protected response is observed without weakening its validation, full-ack checks or quarantine logic. Keep rank12's complete two-commit range. A denied request neither acknowledges nor quarantines rows; all existing queue handling is unchanged.

Regression source: test_t3_sync_auth_health.py exercises actual protected request functions with synthetic response/database adapters, separate phase recovery, public health masking, queue retention, and interrupted cycle reporting. test-t3-sync-auth-health.mjs evaluates the actual footer branch with online/offline public reachability and simultaneous retained authorization faults. No live credentials, real attendance, native models or network calls are required by these fixtures.

Validation here: source edits and git diff --check only. No tests, builds, installs or runtime executed. Root owns serialized exact-head checks and physical/deployed acceptance.
